# 智慧杆資料應用整合工作坊 數據資料包（0930&1007場次）關聯筆記

來源資料夾：`智慧杆資料應用整合工作坊_數據資料包_0930&1007場次/`
規格文件：`數據資料包_欄位一覽表v1.pdf`（定義理想欄位，實際檔案欄位名與此有落差，見下方「規格 vs 實際落差」）

## 0. 總覽：場域與杆體清單

主檔：`杆體資訊_smartpole_list_2026.csv`（欄位：groupid, polename, createdate, placedesc, latitude, longitude, updatetime）
共 15 根杆體，兩個場域：

| 場域 (groupid) | 杆體代號 (polename) |
|---|---|
| 臺北市信義區 | SCCP-SP-01 ~ SCCP-SP-10 |
| 高雄市左營區 | A1 ~ A5 |

**polename 就是各子系統用來關聯回杆體的實際主鍵**（規格書稱之為 poleId，但主檔欄位名其實是 `polename`）。

## 1. 四大類資料夾與對應子系統

| 資料夾 | 子系統 | 資料區間 |
|---|---|---|
| 人流辨識 | 攝影機 AI 影像辨識 | 2025/12 ~ 2026/6 |
| 環境感測 | 溫溼度/PM2.5/PM10/CO 等感測器 | 2025/12/12 ~ 2026/6/30 |
| 路燈照明 | 路燈控制器 | 2025/12/12 ~ 2026/6/30 |
| 智慧電表 | 用電量（總耗能 + 台北設備級細分） | 總耗能 2026/5/1~6/30；台北設備細分 2026/1/1~2/10 |

每類資料夾的檔名都遵循同一套規則：`{類別}numberinfo_114.12-115.04.csv`（民國年區間，較早一段）與`{類別}numberinfo_115.05-115.06.csv`（較新一段），代表同一份資料被拆成兩個時間區段匯出，**欄位結構相同，需要時直接上下合併（concat）即可**。

## 2. deviceid 命名規律 → 這是跨檔案關聯的關鍵

人流辨識、環境感測、路燈照明三個資料夾的原始明細（*numberinfo*.csv）都是「長表格」格式：

```
deviceid, attrid, reporttime, value
```

`deviceid` 前綴代表設備類型：

| 前綴 | 子系統 | 範例 |
|---|---|---|
| `IN30---` | 攝影機（人流辨識） | IN30---1765972800665 |
| `IN21---` | 環境感測器 | IN21---1765521502354 |
| `INL1---` | 路燈控制器 | INL1---1765521500346 |

`attrid` 是量測項目代碼（見下方代號對照表），`value` 是量測值；`reporttime` 是時間戳。也就是說 numberinfo 的每一列 = 一台設備 + 一個屬性 + 一個時間點的一筆數值。**要還原成規格書描述的寬表（一個時間點有 Temp/RH/PM2.5... 多欄），需要以 deviceid + reporttime 做 pivot，attrid 展開成欄名。**

人流辨識另外還有 `camerastringinfo_115.05-115.06.csv`，格式相同但 `value` 是字串/JSON（例如 aiAnalysis 事件的完整 JSON 物件），對應規格書「四、影像辨識」的 `aiAnalysis` 物件欄位（eventId, eventType, eventStartTime, objectType, objectCount, confidenceScore）。**numberinfo 放數值型屬性（如 status=103800）、stringinfo 放字串/JSON型屬性（如 counting 事件的 aiAnalysis 內容），兩者用同一組 deviceid + reporttime 可對齊、互補。**

## 3. 代號對照表（把 attrid / deviceid 轉成人類可讀）

三份對照表都內含「兩張表」：上半部是屬性代碼字典，下半部是 deviceid ↔ polename 對照表（中間用空行分隔）。

- `人流辨識/camerainfo_代號對照.xlsx`
  - 屬性代碼：103901=aiAnalysis原始封包、103902=事件ID、103903=事件類型、103904=事件開始時間、103800=設備運行狀態(0離線/1正常/2警告/3錯誤)
  - deviceid↔polename：group, deviceid, polename（IN30--- 系列 ↔ SCCP-SP-01~10，部分杆體有多支攝影機故重複列出）
- `路燈照明/lightinfo_代號對照.xlsx`
  - 屬性代碼：100800=調光狀態(亮度百分比)、103800=控制器狀態(1連線/3異常/9其他)
  - deviceid↔polename：INL1--- 系列 ↔ SCCP-SP-01~10
- `環境感測/sensorinfo_代號對照.csv`（注意：此檔為 **Big5 編碼**，用 UTF-8 開會亂碼，需以 Big5/CP950 讀取）
  - 屬性代碼：401400=風速、400100=溫度、401500=PM2.5、400200=相對溼度、400700=CO、401900=PM10
  - deviceid↔polename：目前只列出 2 筆範例（IN21---...354 ↔ SCCP-SP-05；IN21---...459 ↔ A2），**很可能不是完整清單**，若要覆蓋全部 15 根杆體的感測器需另外核對 numberinfo 明細裡出現過的所有 deviceid。

⚠️ **注意**：這些對照表裡的 deviceid（IN30/INL1/IN21 開頭）跟智慧電表的 deviceid（IN12 開頭，見下方）**命名體系完全不同、無法互相比對**，只能各自透過 polename 間接對齊到同一根杆體。

## 4. 智慧電表：兩套資料，關聯方式不同

### 4a. 總耗能（各杆體層級，2026/5/1~6/30）
檔案：`智慧電表/115年5月-6月_各杆體總耗能_台北_v2.xlsx`、`..._高雄.xlsx`

- **這兩份 xlsx 用「工作表(sheet)」直接代表杆體**，不是靠欄位裡的 poleId：
  - 台北檔：10 個 sheet，sheet 名稱就是 SCCP-SP-01 ~ SCCP-SP-10
  - 高雄檔：5 個 sheet，sheet 名稱是 A1 ~ A5
- 每個 sheet 欄位：deviceid, reporttime, v(電壓), a(電流), hz, pf(功率因數), w(瞬時功率), whplus(正向累積電量), whminus(逆向電量)
- 台北 deviceid 格式如 `IN12-0011141A6F2C-10`（字串），高雄 deviceid 是純數值型（如 1.03588e+16），兩地格式不同，**deviceid 在此處不是必要的關聯鍵，sheet 名稱(=polename)才是**
- 台北資料頻率高（每杆約13~17萬列，約每3分鐘一筆），高雄較稀疏（每 sheet 約4400~4500列，約每20分鐘一筆）— 兩場域的資料完整度不一致，分析時要留意。

### 4b. 台北場域設備級耗能明細（2026/1/1~2/10）
資料夾：`智慧電表/115年1月-2月_各設備耗能_台北/`，共 4 個 CSV，彼此用外鍵串接成一條鏈：

```
deviceconfig (dcid = 杆體/資料收集器層級)
   └─ dcid ─→ metercircuit (dcid, loadid, loadname, category)  ← 迴路/負載設備清單
                  └─ 迴路對應到電表 meterid（實際電表資料表沒有直接欄位名叫 loadid→meterid，
                     需透過 circuitid/meterid 命名慣例或另外核對，見下方待確認事項）
meterprofile (meterid, dcid, circuitid, ...)  ← 最新狀態快照，含 dcid + circuitid 可回頭對到 metercircuit / deviceconfig
meterinfo2   (meterid, updatetime, reporttime, v, a, hz, pf, w, whplus, ...) ← 歷史逐筆紀錄，只有 meterid，沒有 dcid
```

- `deviceconfig.dcid` = 杆體層級的資料收集器編號，**可透過 latitude/longitude 直接比對回杆體資訊主檔**：
  - 例：deviceconfig 裡 dcid=11221, lat=25.043868, lon=121.55906 ⇔ 主檔 SCCP-SP-01 (lat=25.043868, lon=121.55906) 完全一致 → **緯經度是 deviceconfig ↔ polename 最可靠的關聯鍵**（因為 devicename 欄位本身編碼是亂碼，不可直接使用；detected 需要用 Big5/CP950 重新解碼才能看懂，目前顯示為亂碼片段）
  - dcid=11215, lat=25.044946, lon=121.56047 ⇔ SCCP-SP-04，以此類推。
- `metercircuit.dcid` 與 `deviceconfig.dcid` 同一欄位，直接可 join，取得每個杆體底下有哪些負載設備（loadid, loadname, category）。
- `meterprofile` 同時有 `meterid` 與 `dcid` + `circuitid`，是三張表的橋樑：可用 `meterprofile.dcid` join `deviceconfig.dcid`（→ 杆體），也可用 `meterprofile.circuitid` join `metercircuit.circuitid`（→ 負載設備名稱），再用 `meterprofile.meterid` join `meterinfo2.meterid`（→ 歷史逐筆用電數據）。
- `meterinfo2` 只有 `meterid`，是最細的時序資料表，**必須先經過 meterprofile 才能知道某個 meterid 屬於哪根杆體、哪個迴路/負載**。

## 5. 規格 vs 實際落差（重要，避免直接照 PDF 欄位名去寫程式）

| 規格書欄位 | 實際檔案情況 |
|---|---|
| `poleId` | 主檔欄位其實叫 `polename`（字串如 SCCP-SP-01），且是各子系統對照表/sheet名稱使用的實際鍵值，PDF 裡描述的 poleId 建議用 UUID，但實務上用的是這組人類可讀代號 |
| 各子系統的寬表（Temp/RH/PM2.5 同一列） | 環境感測/路燈/人流辨識原始檔其實是「長表格」(deviceid, attrid, reporttime, value)，需要自行 pivot attrid 才能得到規格書描述的欄位結構 |
| `DEVSNo` | 對應到各 numberinfo 檔案裡的 `deviceid` 欄位 |
| 智慧電表(一)的 `poleId`, `DEVSNo` | 115年5-6月總耗能 xlsx 實際上沒有 poleId 欄位，是用 Excel 分頁(sheet)代表杆體；DEVSNo 對應 `deviceid` |

## 6. 待確認 / 建議下一步

1. `環境感測/sensorinfo_代號對照.csv` 的 deviceid↔polename 對照只給了 2 筆範例，需要從 numberinfo 明細抓出所有出現過的 IN21--- deviceid，確認是否 15 根杆體都各有一顆環境感測器。
2. deviceconfig 的 `devicename` 欄位是亂碼，原始編碼推測為 Big5/CP950，但用該編碼重新解碼後仍有殘缺字元（可能原始匯出時已經雙重編碼損毀），若需要人類可讀的杆體別名，建議直接用經緯度比對主檔，不要依賴 devicename。
3. `metercircuit` 的 `loadid`/`category` 目前看到的樣本都是空值或代碼（如 "0","1"），沒有另外的 category 代碼字典，若要分類設備用途（如照明/監視器/電表本身）需再找是否有額外的說明文件。
4. 高雄場域的環境感測/路燈/人流辨識三個子系統目前只在 sensorinfo 對照表看到 A2 一筆，需確認 A1/A3/A4/A5 是否也有對應設備資料，或高雄場域這三類資料本身就不完整（只有智慧電表總耗能有涵蓋 A1~A5）。
